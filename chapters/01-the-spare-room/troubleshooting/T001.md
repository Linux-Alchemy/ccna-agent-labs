## Ticket

> My workstation cannot reach the development server at 192.168.0.3. It can still reach the external test address, 1.1.1.1.

**Impact:** Joe could not establish connectivity to the local development server from his workstation.

**Initial observations:** PC0’s ping to `192.168.0.3` failed; an external destination remained reachable. The supplied server ping showed 4 sent and 0 received. The supplied external ping had an initial timeout followed by two replies before interruption; it established reachability, not a clean loss-free test. No cause is asserted for that timeout.

**Completion criteria:** Restore PC0 connectivity to the server and its website by name, preserve reachability to both simulated ISP loopbacks, explain the repair and save the exercise copy.

## Investigation

| Step | Check / action | Finding and reasoning |
|---|---|---|
| 1 | Checked PC0’s IP and DNS settings and connectivity to other endpoints. | Client settings were correct and other endpoints were reachable, so Matt continued at the server. |
| 2 | Inspected DustyServer with `ipconfig /all`. | Its address was `192.168.0.30`, rather than the expected `192.168.0.3`; its mask and gateway were correct. |
| 3 | Corrected the server address and checked it again. | After-output showed `192.168.0.3/24`, gateway `192.168.0.1` and DNS `192.168.0.3`. |
| 4 | Retested connectivity and saved the exercise. | Server ping and website access returned. Matt confirmed both external destinations still worked, and the tutor verified the saved repair. |

## Assistance

No diagnostic hints requested or given; no answer requested or revealed. The tutor supplied the ticket/preflight checks, summarised Matt’s notes and requested final acceptance-test confirmation.

## Resolution

**Cause:** DustyServer’s static IPv4 address did not match the address clients were using to reach it.

**Repair performed by Matt:**

```text
ipconfig 192.168.0.3 255.255.255.0 192.168.0.1
```

The repair restored the expected address while retaining the subnet mask and default gateway. DNS remained set to `192.168.0.3`.

## Takeaway

Check the client first, then the affected endpoint. Correct client settings and successful connectivity elsewhere help narrow the investigation; the server still needs the address clients expect. Verify the repaired service and a previously working path before closing the ticket.
